## 1. Executive summary

**Overall health: 🚨 Critical issues.**

The core is compact and well tested: signals, the reconciler and the DSL pass 560 tests. The trouble is where types
cannot help:

- **Native lifetimes:** GC thread state, FFI exception unwinding and GTK object ownership.
- **Host wiring:** `UiThread` is never installed.
- **Build surface:**
    - The groupId is split between `net.leibman` and `dev.thicket`.
    - Renderers and examples are outside the root aggregate.
    - `testFull` runs out of memory at the default heap.

**Most critical:** the groupId split from #70. `build.sbt:10` says `net.leibman`, but the sbt plugin and templates
hard-code `dev.thicket`. The next published plugin would point users at artefacts that don't exist.

Close behind are two memory-safety bugs:

- `GcState.guarded` is not re-entrant. A nested GTK signal marks the main thread Unmanaged while Scala is still running
  on it.
- Closing a GTK sheet with the window's close button frees content that the `GtkWindow` still points at.

**Biggest cross-cutting pattern:** per-handle state lives in many parallel maps, each released by hand in `destroy`.
Four reviewers independently found five leaks of this one shape, and the leak checks themselves have blind spots.

### P0-2 `GcState.guarded` is not re-entrant [L/M]

- **Where:** `modules/renderer-gtk/src/main/scala/thicket/renderer/gtk/GcState.scala:42-46` and
  `modules/renderer-apple/.../GcState.scala:51-55`.
- **Path:**
    1. `GtkRenderer.scala:309` calls `gtk_editable_set_text`.
    2. GTK emits `changed` synchronously, which runs the `changed` trampoline (`Handles.scala:134-137`) inside
       `guarded`.
    3. When that inner trampoline returns, its `finally` sets the thread Unmanaged while the outer Scala frame is still
       running.
    4. The same happens at `GtkRenderer.scala:345, 353, 451, 498, 867` (switch, check, drop-down, range, toggle).
- **Impact:** the GC can miss the main thread's roots during a collection started by a worker thread. That is heap
  corruption or use-after-free, the same class of bug S3 and S9 dealt with. A TextField with initial text hits this at
  mount.
- **Fix:** count the depth, so that only the outermost entry and exit change state; make the counter thread-local if
  callbacks can arrive on several threads. Apply it to both copies. De-duplicate the copies later (P3-6).
- **Sources:** F-H1.
- **Verified:** yes.
- **Verify:**
    - GTK gallery and counter self-tests.
    - A new step: a click sets a TextField's `Var` while a worker forces GC.
    - On the Mac: `bin/verify-apple.sh`.

### P0-3 No exception barrier at FFI entry points, and one failing effect breaks every later write [L; Apple part L/M]

- **Where (a):** every trampoline in GTK `Handles.scala` (94, 134, 152, 166, 178, 207, 241, 276); `GtkApp.scala`
  (`onActivate`, `onPopped`, `onBack`); Apple `Handles.scala:148-213`; `AppleApp.onReady`. `guarded` has a `finally` but
  no `catch`. `VirtualRows.bind` throws by design (`Reconciler.scala:328, 330, 345`) and is called from `listBind`.
- **Where (b):** `signals/.../Core.scala:235-265`. `flush` puts a failed effect back on the queue and rethrows, so every
  later unrelated `Var.set` runs it again and throws.
- **Impact:**
    - A throw in app code unwinds through GTK/Swift C frames. That is undefined behaviour, in practice an abort with no
      stack trace.
    - Because of (b), every later click aborts too.
    - On Android, the throw escapes the `OnClickListener` and kills the app.
- **Fix:**
    - In the trampoline wrapper: `guarded { try body catch { case NonFatal(e) => ErrorSink.report(e) } }`, where the
      sink can be installed and logs by default. Value-returning trampolines return null or 0.
    - In `flush`: stop re-running a failed effect until one of its dependencies changes (or retry a bounded number of
      times). Do not rethrow to an unrelated writer.
- **Sources:** F-H3.
- **Verified:** yes.
- **Verify:**
    - A signals spec: an effect throws once, and a later unrelated write does not throw.
    - A GTK self-test step with a throwing handler: the error is logged and the app keeps running.

### P0-4 GTK: closing a sheet with the window's close button causes a use-after-free [L]

- **Where:** `GtkRenderer.scala:1137-1151`.
- **Path:**
    1. The close-request callback calls `sheetWindow.remove(handle)`, then `f()` (the app's `OnDismiss`).
    2. The app unmounts synchronously (`Signal.scala:134-141`).
    3. `destroy` (`:1096-1119`) no longer finds the sheet window, so it takes the plain-widget path and calls
       `gtk_widget_unparent(handle)` (`:1114`) on the window's child.
    4. `Handles.closeRequest` returns FALSE (`Handles.scala:233-237`), so GTK then destroys a window whose child pointer
       refers to freed memory.
- **Impact:** the gallery sheet (`Gallery.scala:320-328`) and the documented pattern give GTK_IS_WIDGET criticals or a
  crash on an ordinary user action. Only the app-initiated close is tested (`counter-gtk Todo.scala:384-391`). This
  might be linked to P2-20.
- **Fix:** keep the `sheetWindow` entry, so `destroy` takes the `gtk_window_set_child(win,null)` + `gtk_window_destroy`
  path. Return TRUE (veto the close) and let the unmount destroy the window (D10).
- **Sources:** R-H2.
- **Verified:** yes, including `dismiss` at `:1209-1218`.
- **Verify:** a self-test step that emits `close-request` on the sheet window, then checks there is no critical on
  stderr and that `liveCount` is back to baseline.

### P0-5 No host installs `UiThread` [L; Apple install L/M]

- **Where:** `core/.../UiThread.scala:30`; the default poster is `f => f()`.
    - `git grep UiThread.install` finds only tests (`EffectZioSpec.scala:146`, `TestUiThread.scala:39`) and spike S9.
    - The hosts install only `ThreadGuard`: `GtkApp.scala:376`, `AppleApp.scala:131`, `MainActivity.scala:50`,
      `GalleryActivity.scala:48`.
    - The writes happen at `effect-zio/.../syntax.scala:38, 63-64, 83, 102, 117-121`.
    - A second, parallel seam, `Renderer.runOnUiThread` (`Renderer.scala:836`), is implemented by all three renderers
      and never called.
- **Impact:** on every real host, `asSignal` completes on a ZIO worker thread and `ThreadGuard` throws there. The defect
  is swallowed (P1-5), so the screen shows `Loading` forever and nothing is logged. Without the guard, the signal graph
  is mutated from several threads. No example uses effect-zio, so nothing has hit this yet.
- **Fix:**
    - Each host calls `UiThread.install(renderer.runOnUiThread)`, or `GtkApp.postToUi`/`AppleApp.postToUi`/
      `handler.post`, next to `ThreadGuard.install`.
    - Make the default fail loudly.
    - Mark `poster` `@volatile`.
    - Later, replace the two calls with one `Host.install`.
    - Add an effect-zio use to the gallery or the todo app.
- **Sources:** F-H2, A-HIGH-1, D-E.
- **Verified:** yes.
- **Verify:** a GTK self-test step where `ZIO.succeed(1).asSignal` reaches `Done`; the Android SelfTest on AVD s2test;
  the Mac `verify-apple.sh`.

## 7. Cross-cutting patterns

1. **Teardown is the weak path everywhere** (F, S, A, P and R all touch it):
    - five leaks of one shape (P2-2 to P2-6) plus P2-8;
    - leak checks with blind spots (P2-5);
    - O (n) removal paths (P2-10, P2-11);
    - `discard` never called;
    - native frees on paths the user starts (P0-4, P1-7).

   The fix is P3-1 plus a mount/unmount stress self-test that asserts on `liveCount`, owner child counts and wall time:
   10k rows, a shared signal, theming, a LazyColumn and a Sheet close. Several reviewers proposed that test
   independently.
2. **Nobody owns failure handling.** A thrown exception does damage at five layers:
    - it aborts through the C frames (P0-3a);
    - it poisons the runtime (P0-3b);
    - it kills the effect for good (P1-6a);
    - effect-zio swallows it (P1-5);
    - it corrupts the reconciler (P1-7).

   One `ErrorSink` in core could cover all five.
3. **Host wiring is incomplete and copied per platform:**
    - UiThread is never installed (P0-5);
    - page owners are detached on GTK and Android (P2-19);
    - the host layer is copied three times (P3-3);
    - the Android gallery has no host at all (P1-14).
4. **TestRenderer is more forgiving than the real renderers.** It re-binds on invalidate (P1-3) and only records props.
   The gallery, which is meant to be the safety net, is not built on Android (P1-14) and doesn't show the states that
   break (P2-23). Every P1 renderer bug was invisible to the 560 green tests.
5. **#70 carried build changes nobody reviewed:** org, baseVersion, publishTo, scmInfo and the ThisBuild removal (P0-1,
   P1-2). Four reviewers landed on `build.sbt:10`. Without Linux CI (P2-21) and with the renderers outside the aggregate
   (P1-1), nothing would have flagged it.
6. **The docs freeze rule causes the drift.** CLAUDE.md forbids touching docs/12-15 even though they are meant to be
   living docs, which is how P3-17 and P3-18 happened.
